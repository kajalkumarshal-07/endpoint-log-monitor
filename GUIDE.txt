================================================================================
 ENDPOINT LOG MONITOR - FUNCTIONALITY GUIDE
 Reads ConfigMgr / ccmsetup / Intune / MDM client logs, groups the errors that
 need action, attaches known troubleshooting steps, decodes error codes and
 exports reports. Windows GUI, PowerShell 5.1 + WinForms.
================================================================================


--------------------------------------------------------------------------------
 1. WHAT IT IS
--------------------------------------------------------------------------------

Endpoint Log Monitor is a single-folder PowerShell application. It walks the
client log files on this PC (or on another PC over your admin share), pulls out
the warnings and errors, collapses repeats into one row per real problem, tells
you what it means and how to fix it, and lets you trigger the ConfigMgr client
cycles that usually clear it - all from one window.

Design rules it follows:

  * Nothing leaves your network. It reads log files and one Windows event log.
    No telemetry, no uploads, no agent installed on the target.
  * Your rules are yours. Rules.json is only ever written when you explicitly
    hide a pattern; fixes you add are never overwritten.
  * Nothing destructive by default. Client actions are the same actions a tech
    would run by hand; the only destructive one (clear ccmcache) asks first.


--------------------------------------------------------------------------------
 2. HOW TO RUN IT
--------------------------------------------------------------------------------

  powershell -ExecutionPolicy Bypass -File .\EndpointLogMonitor.ps1

Parameters (both optional):

  -ComputerName <name>   Pre-fill the DEVICE box and auto-scan that machine
                         as soon as the window opens.
  -RulesPath <path>      Use a different rules file than .\Rules.json.

Examples:

  .\EndpointLogMonitor.ps1
  .\EndpointLogMonitor.ps1 -ComputerName PC-042
  .\EndpointLogMonitor.ps1 -RulesPath "\\share\team-rules.json"

Requirements: Windows PowerShell 5.1 (built in on Windows 10/11),
System.Windows.Forms (part of Windows). Run from any location - the script
finds its sibling files relative to itself. ExecutionPolicy Bypass is the
simplest way to launch it; nothing else needs installing.

If you do NOT pass -ComputerName the window opens idle ("Ready. Click Scan
logs...") so you can see the layout first. With -ComputerName it scans on open.

--------------------------------------------------------------------------------
 5. HOW A SCAN WORKS (THE PIPELINE)
--------------------------------------------------------------------------------

Clicking Scan logs runs this sequence (Invoke-LogScan -> New-IssueRows):

  1. RESOLVE ROOTS
     Local (blank DEVICE) or remote (\\PC\admin$ ...). Missing folders are
     reported in the progress line, not as errors. The Demo data button
     substitutes its own folder here (section 13).

  2. ENUMERATE FILES
     *.log and *.lo_ in each root folder (top level only, no recursion).

  3. PARSE EACH FILE, streaming with FileShare.ReadWrite so a log that is
     being written to right now still opens:
       - CMTrace format   <![LOG[message]LOG]!><time=".." date=".."
                          component=".." type="1|2|3" ...>
                          Multi-line messages are joined with newlines.
       - Legacy SMS       "message  $$<Component><MM-DD-YYYY hh:mm:ss.fff-60>
                          <thread=...>"
       - Anything else    treated as a plain-text line, severity guessed from
                          the words in it.
     Severity source: CMTrace type attribute (1 = info, 2 = warning,
     3 = error) when present; otherwise the keyword heuristic (error, failed,
     fatal, exception, denied, cannot, could not, unable -> error;
     warning, retry, timeout, not found, skipping -> warning).

  4. CAPTURE FILTER
     Entry kept when: type >= 2 (warning/error), OR "Include informational
     lines" is ticked. Same rule is applied to the event log entries, so the
     switch behaves identically everywhere.

  5. MDM EVENT LOG
     Microsoft-Windows-DeviceManagement-Enterprise-Diagnostics-Provider/Admin
     (up to 1500 events), shown as MDM-Diagnostics.evtx. Levels map to
     Critical/Error -> error, Warning -> warning, else info.

  6. HIDDEN then NOISE
     Hidden (yours) matches remove the line and are counted for the status
     bar. Noise (built in) matches remove it silently.

  7. EXTRACT ERROR CODES from the message (see section 7).

  8. NORMALISE + GROUP (see section 6). Each group accumulates: count,
     first-seen, last-seen, worst severity, the code list, and up to 4
     sample lines.

  9. MATCH A FIX
     First by code (index of every code/aliasCode in Rules.json), then by a
     regex `match` field on the raw message. Title + first hex code becomes
     the Issue text; "Fix = Yes" when the matched fix has steps.

 10. BUILD ROWS + SORT
     Severity rank, then count descending, then issue. Bind to the grid and
     select the first row so the detail pane is never empty after a scan.

Hard limits (protection against a runaway directory):
  400,000 captured entries per scan, 20,000 distinct groups, 1500 MDM events.


--------------------------------------------------------------------------------
 6. GROUPING - WHY 500 LINES BECOME ONE ROW
--------------------------------------------------------------------------------

A problem like "App installation failed with error 0x87D00324" repeats hundreds
of times with different GUIDs, times and numbers. Grouping keys on:

    <log file> | <normalised message> | <known codes in it>

Normalisation (ConvertTo-NormalisedShape) rewrites the volatile parts:

  {12AB...-...}  or (12AB...-...)  or bare GUID   ->  <G>   (brace style kept
                                                       in the surrounding
                                                       text so {GUID} and
                                                       (GUID) end up equal)
  14:05:09.123 or 1:2:3                            ->  <T>
  0x87D00324 / 0x80070643                          ->  <H>
  any 4+ digit run                                 ->  <N>
  runs of whitespace                               -> single space

Two lines from the same log with the same shape but different GUIDs/times
therefore land in one group with Count = n. Codes are also part of the key:
if one instance carries a known code and another does not, they stay separate,
because the actionable problem is different.

The same normaliser is used to build "hide this pattern" regexes, which is
why hiding survives changing GUIDs and timestamps.


--------------------------------------------------------------------------------
 7. ERROR CODE DECODING
--------------------------------------------------------------------------------

Codes are harvested from a message by three rules (Get-CodesFromMessage):
  * hex literals  0x87D00324 (4-8 hex digits)
  * large decimals -2016410844 / 2278556452 (6-10 digits, not glued to a word
    or a dot so versions are skipped)
  * "exit code 1618" / "return code" / "error code" / "result code" patterns
    -> MSI:n, plus the wrapped form 0x80070000 + n

Normalisation (ConvertTo-CanonicalHex) turns any of those into one canonical
'0xXXXXXXXX' form, so 0x87D00324, -2016410844 and 2278556452 are the same key.

Decoding rules used by the Error codes tab:

  * hex input                       -> unsigned = value, signed = reinterpret
                                       as int32, canonical = 0x%08X
  * negative decimal                -> unsigned = value + 2^32
  * positive decimal > 2^31-1       -> signed = value - 2^32, note added
  * 0x80070000 .. 0x8007FFFF       -> HRESULT_FROM_WIN32:
                                       Win32 = unsigned - 0x80070000
                                       if that is <= 65535 it is also the raw
                                       MSI/Win32 exit code
  * value <= 65535                  -> treated as a raw MSI / Win32 exit code
                                       (1618, 3010, 1641, ...)

Lookup order for the meaning/steps: exact hex in Rules.json -> "MSI:n" entry
-> wrapped 0x8007xxxx form.

Worked examples:

  0x87D00324   = -2016410844 = 2278556452   App installed but detection
                                             method did not find it
  -2016345060  = 0x87D1041C                  (same class of ConfigMgr code)
  0x80244022   = -2145107934                 WU: service reset / update
                                             download problem
  0x80070643   = Win32 1603                  MSI fatal error during install
  1618         = 0x00000652 / MSI:1618       Another installation is already
                                             in progress
  0x8018002B   = -2145910741                 MDM: enrollment / policy problem
  3010         = success (reboot required)   never treated as a failure

Confidence labels in Rules.json: verified (checked against Microsoft docs),
community (field reports), unverified (best effort). Current file: 76
verified, 14 community, 1 unverified.


--------------------------------------------------------------------------------
 8. RULES.JSON - THE SHARED KNOWLEDGE FILE
--------------------------------------------------------------------------------

Shape:

  {
    "version": 1,
    "fixes":  [ ... ],
    "noise":  [ "regex", ... ],
    "hidden": [ "regex", ... ]
  }

A fix entry:

  {
    "codes":      [ "0x87D00324", "-2016410844", "2278556452" ],
    "aliasCodes": [ "..." ],              optional, indexed like codes
    "match":      "(?i)regex on message", optional, fallback when no code hits
    "title":      "App installed but detection method did not find it",
    "logs":       [ "AppEnforce.log", "AppDiscovery.log" ],
    "confidence": "verified",             verified | community | unverified
    "steps":      [ "Check the exit code and command line in AppEnforce.log...",
                    "Re-run the Application Deployment Evaluation Cycle..." ]
  }

  * codes may be hex, signed, unsigned or a small MSI number - all forms are
    normalised to one index key.
  * steps are what you see in WHAT TO DO and in the HTML report.
  * `match` is a .NET regex tested against the raw message; it is how 9 of the
    current entries work (problems that carry no stable code).

A noise entry is a regex; matching lines are dropped (silently).

A hidden entry is the same idea, but for patterns YOU suppressed from the
right-click menu. It is stored as a normalised-shape regex, so volatile parts
stay wild. The status bar counts how many lines your hidden rules removed.

Current contents: 91 fixes, 22 noise patterns, 0 hidden.

Adding your own:

  1. Open rules file (toolbar button) or edit Rules.json directly.
  2. Copy an existing fix block; change codes/title/logs/steps.
  3. Save as UTF-8. The next scan picks it up (or click Re-scan).
  4. If the JSON is invalid you get a clear message box and the tool falls
     back to an empty ruleset - it will not crash or silently ignore it.

The file is created automatically the first time it is needed and is never
rewritten by the tool except when you choose "Hide this pattern".


--------------------------------------------------------------------------------
 9. CLIENT ACTIONS - WHAT EACH ONE DOES
--------------------------------------------------------------------------------

All of them target the DEVICE box (blank = this machine). Every action returns
OK or FAIL into the console log; nothing throws out of the UI.

ConfigMgr cycles (Invoke-CimMethod, root\ccm, SMS_Client.TriggerSchedule):

  Machine Policy Retrieval & Evaluation Cycle         {..0021} {..0022}
  User Policy Retrieval & Evaluation Cycle            {..0025} {..0026}
  Application Deployment Evaluation Cycle             {..0121}
  Software Updates Scan Cycle                         {..0113}
  Software Updates Agent Assignment Evaluation        {..0108}
  Hardware Inventory Cycle                            {..0001}
  Software Inventory Cycle                            {..0002}
  Discovery Data Collection (Heartbeat)               {..0003}
  Refresh Location Services                           {..0024}
  Agent Cleanup Request                               {..0040}

  "Run all client cycles" runs all ten in order and logs a start/end banner.

Services:
  Restart CCM client service (CcmExec)      Restart-Service, local or remote
  Restart Windows Update service (wuauserv) same

Maintenance:
  Clear ccmcache          deletes the cached content folders under
                          Windows\CCM\CcmCache (local) or \\PC\admin$\...
                          - asks for confirmation first, then reports the
                          folder count before/after.
  Trigger Intune / MDM sync   starts the scheduled tasks under
                          \Microsoft\Windows\EnterpriseMgmt\* (Schedule* and
                          *enrollment*), locally or via a CIM session.
                          Fails with a clear message if the device is not
                          MDM-enrolled.

Note: on a machine with no ConfigMgr client installed, the cycle triggers will
return FAIL (no root\ccm namespace) - that is the correct, informative answer,
not a crash.

--------------------------------------------------------------------------------
 11. SCANNING ANOTHER MACHINE
--------------------------------------------------------------------------------

Type a computer name in DEVICE (or pass -ComputerName). It reads:

  \\PC\admin$\Windows\CCM\Logs
  \\PC\admin$\Windows\ccmsetup\Logs
  \\PC\C$\ProgramData\Microsoft\IntuneManagementExtension\Logs
  the MDM event log on that PC (Get-WinEvent -ComputerName)

What you need on the target:
  * administrative share access (an admin on that PC, or equivalent rights)
  * the folders to exist (a PC without the ConfigMgr client simply has no
    CCM\Logs - reported as "not found" in the progress line)

What it does NOT need: an agent, a server, an open firewall port beyond the
normal admin share, or any change on the endpoint. Client actions on a remote
PC use the same shares/CIM, so the same rights apply.

If nothing comes back, check: name resolves, you are admin there, and the
device is actually managed (the About tab lists the exact paths it reads).

 12. WHAT IT READS ON THIS MACHINE (EXAMPLE)

Local roots:
  C:\Windows\CCM\Logs
  C:\Windows\ccmsetup\Logs
  C:\ProgramData\Microsoft\IntuneManagementExtension\Logs
  Microsoft-Windows-DeviceManagement-Enterprise-Diagnostics-Provider/Admin

  1 issues from 1 log files (2 entries read, 0 hidden by your rules).

That is expected - the tool reports what it found rather than inventing data.
On a properly managed endpoint you get the full set of client logs.

--------------------------------------------------------------------------------
 14. LIMITS AND SAFETY
--------------------------------------------------------------------------------

  * Windows only (WinForms). Tested on Windows PowerShell 5.1.
  * Reads *.log and *.lo_ at the top level of each root; subfolders are not
    walked. A .lo_ that is actually a compressed archive is read as text and
    falls back to the plain-text parser.
  * Grouping keeps at most 4 sample lines per issue and 20,000 groups per
    scan; 400,000 entries is the hard read cap.
  * It never modifies a log file (opens with FileShare.ReadWrite).
  * It never deletes anything except ccmcache content, and only after you
    answer Yes to the prompt.
  * Rules.json is the only file it writes (plus your chosen export files).
  * No network calls other than the admin shares / CIM / event log of the
    machine you named.


--------------------------------------------------------------------------------
 15. TROUBLESHOOTING
--------------------------------------------------------------------------------

  "Nothing appears after a scan"
    The tool only keeps warnings and errors unless you tick "Include
    informational lines". A clean device legitimately shows no rows.

  "Scan failed: ..." in the status bar
    Usually the remote name or share is unreachable. Try the local scan
    (blank DEVICE) first to confirm the tool works.

  "Rules.json could not be parsed"
    Fix the JSON (the message box shows the line). The tool runs with an
    empty ruleset meanwhile - rescans will still work.

  "no root\ccm namespace" from client actions
    That PC has no ConfigMgr client; the cycle cannot be triggered there.

  A problem keeps coming back after I hid it
    Hide from the right-click menu (not by hand) - the generated pattern
    ignores GUIDs/times/codes, so it keeps matching. Hand-written patterns
    are easy to over-fit.

  The window looks wrong on a very small display
    Minimum supported size is 1320 x 760; below that Windows clamps the
    form and things may clip. Maximize on a 1366x768 or larger screen.
